# Adaptive mining-model tournament design

Date: 2026-08-08

## Context and approval

The first eight-model comparison completed its calls but did not identify an
eligible mining model. Every candidate had at least one hard failure under the
old request and scoring contract. The controllable prompt, completion,
reasoning, provenance, and corpus-scoring causes have since been mitigated and
verified locally. The user approved an adaptive tournament to produce
selection-grade evidence without exceeding the remaining OpenRouter benchmark
budget of `$2.9651080226`.

The tournament compares models; it does not write to `claw.db`, change the
active model profile, or mine repositories into the live corpus.

## Considered approaches

### 1. First-round rerun only

Run all eight candidates against the three production fixtures and rank the
result. This fits the remaining budget but cannot establish held-out quality or
repeat stability.

### 2. Adaptive staged tournament

Run the first round, exclude ineligible models, then freeze and authorize only
the held-out and repeat calls that fit the remaining budget. This preserves a
hard budget while directing later spend toward viable candidates. This is the
approved approach.

### 3. Fully reserved tournament

Reserve the worst case for all stages before the first call. The previous
catalog snapshot required `$3.944622607`, approximately `$0.98` more than the
remaining authorization. It is unnecessary when later stages can be selected
from evidence generated by earlier stages.

## User workflow

The CLI remains deliberately two-phase:

1. A prepare command refreshes the live catalog, freezes fixtures, prices the
   requested stage, and writes a plan without paid calls.
2. A run command executes only calls in that frozen plan.
3. A report command scores the completed stage against an explicitly pinned,
   immutable CAM corpus.
4. An advance command selects eligible candidates, verifies the cumulative
   budget, and freezes the next stage without paid calls.

The intended operator flow is:

```text
cam models benchmark plan ... --stage first-round
cam models benchmark run ...
cam models benchmark report ...
cam models benchmark advance ... --stage heldout
cam models benchmark run ...
cam models benchmark advance ... --stage repeat
cam models benchmark run ...
cam models benchmark select ...
```

No command in this flow promotes a model profile automatically. Existing
profile commands remain the explicit activation boundary.

## Frozen stage plans

Each stage plan contains only the calls it can execute:

- `first-round`: all configured candidates across the three first-round
  fixtures;
- `heldout`: up to four eligible first-round candidates across both held-out
  fixtures; and
- `repeat`: up to two eligible finalists on one first-round fixture.

Every plan records the parent run, cumulative prior spend, remaining authorized
budget, selected candidates, exclusion reasons, prompt and catalog digests,
maximum call costs, and no-fallback requirement. A stage refuses to plan if its
worst-case cost exceeds the remaining authorization. When fewer candidates fit,
the advance command selects the largest evidence-ranked prefix that fits; it
never silently increases the budget.

Catalog and prompt digests are frozen per stage. Later stages may refresh the
live catalog for current availability and price, but their receipts preserve
the exact snapshot used for authorization.

## Eligibility and advancement

A model is eligible for advancement only when all expected calls for the stage
completed and the grounded scorer reports no hard failures. Truncated output,
malformed or unsupported envelopes, missing or escaping source files, secret-
like output, provider/model identity drift, and missing calls are exclusion
conditions.

Eligible candidates are ordered deterministically by:

1. higher worst-fixture quality;
2. higher average quality;
3. lower cost per accepted finding;
4. lower total cost;
5. lower synchronous latency when both candidates are synchronous; and
6. model identifier as a stable final tie-breaker.

Batch latency is labeled separately and is not compared directly with
synchronous latency.

The repeat stage uses one previously seen first-round fixture with the same
frozen prompt and request controls. Its result is compared with the original
call to measure output validity, quality variance, finding-count variance, and
cost variance.

## Selection report

The final report does not collapse all evidence into one opaque score. It
produces evidence-backed role candidates:

- `quality`: highest eligible held-out quality, using worst-fixture quality as
  the primary guard against one strong outlier;
- `budget`: lowest cost per accepted grounded finding among eligible models;
- `fast`: lowest synchronous latency among eligible synchronous models; and
- `batch`: strongest eligible queued-batch model, if one survives.

For every role the report includes the supporting metrics, disqualifications,
catalog price snapshot, actual spend, cumulative conservative upper bound, and
the exact explicit promotion command. If no model satisfies a role, the report
says so rather than choosing an ineligible candidate.

## Budget and recovery behavior

The original authorization is `$5.00`. Evidence-backed prior spend is carried
into the tournament ledger conservatively, leaving `$2.9651080226`. Each new
plan and run stores both stage and cumulative spend. Provider-reported cost is
preferred; catalog estimation is used when the provider omits cost.

The harness stops before a call whose maximum cost would exceed the remaining
authorization. Completed receipts are resumable and are charged exactly once.
Failed calls retain redacted receipts and any provider-reported cost. Retry is
explicit; the harness does not switch models or providers.

## Artifacts and safety

Each tournament directory contains content-addressed fixture receipts, catalog
snapshot receipts, stage plans, call receipts, raw responses, quality reports,
advancement decisions, and a final Markdown/JSON selection report. Raw paid
responses and secret-bearing configuration remain local and ignored by Git.

The scorer opens `/Volumes/WS4TB/repo622sn/CAM_CAM/claw.db` read-only and
immutable. Tournament execution never writes to the corpus, mining registry,
mining outcomes, or model profiles.

## Verification

Tests must prove:

1. stage plans contain only their own executable calls;
2. cumulative prior spend reduces the available hard budget;
3. advance excludes missing-call and hard-failed candidates;
4. advancement ordering and budget contraction are deterministic;
5. repeat plans preserve the chosen prompt and request controls;
6. resumed receipts are not charged twice;
7. final role selection uses held-out and repeat evidence where available;
8. no eligible candidate yields an explicit no-selection result;
9. reports include exact promotion commands without performing promotion; and
10. benchmark paths do not write to the pinned corpus or profiles.

Focused benchmark, scoring, CLI, profile, LLM, and miner tests run first. The
broader mining/model suite and `git diff --check` are the final local gates
before a paid stage is planned.
